# 产品相邻性与阻断分流标准 v1.0

> **状态：现行产品决策标准。** 当任务提供推荐产品、产品能力与主任务不完全一致，或产品只可能服务于后续素材/场景时，所有类型必须先执行本标准，再决定 `formal_method`、`ultra_tip`、`related_supplement` 或 `excluded`。本标准防止把能力不匹配过早扩大为整篇文章阻断，同时不允许把不支持的能力包装成解决方案。

## 1. 先区分三件事

1. **主任务匹配**：产品是否直接处理主查询的对象，并完成读者的核心结果？
2. **相邻需求匹配**：主任务完成后，读者是否会在同一工作流、同一资产生命周期、同一发布决策或同一受众路径中自然遇到一个次级需求？
3. **露出安全性**：是否存在已核验的产品能力、明确的对象/格式限制和不会让读者误以为产品解决主任务的写法？

“主任务不匹配”只否定 `formal_method`，不自动否定相邻性。反之，出现同一个平台名称、关键词或商业目标也不自动构成相邻需求。

## 2. 强制五项相邻性判定

在把产品降级或排除前，逐项记录以下结论与证据：

| 判定 | 必须回答的问题 | 通过条件 |
| --- | --- | --- |
| A. 读者后续需求 | 主任务结束后，读者会自然处理什么次级对象、素材或发布决策？ | 是真实的下一步，不是为了露出而制造的假设 |
| B. 工作流关系 | 两个任务如何相连？ | 同一创作者/运营流程、同一资产生命周期、同一页面/发布决策，或有 SERP/关键词/用户资料证据的稳定 follow-on need |
| C. 能力可核验 | 产品能处理该次级对象/格式/动作吗？ | 当前官方产品页、官方帮助/指南及对象/格式专页中至少有直接证据；记录日期与 URL |
| D. 读者决策价值 | 该补充能帮助读者少犯错、完成相邻资产、或作出后续选择吗？ | 有清楚的场景、限制和可执行的最小步骤 |
| E. 不可替代主任务 | 如何防止读者误读？ | 第一屏明说产品不完成主任务的哪一部分；不进入主答案、主方法、排名/比较结论或主 CTA |

`A–E` 均通过，才可让产品进入正文。任一项证据不足时，先保留为 `research_incomplete` 或 `scoped_exclusion`，继续完成与产品无关的研究和文章；不得把整篇任务提前停掉。

## 3. 角色与位置

| 角色 | 何时使用 | 位置与必须写明的内容 |
| --- | --- | --- |
| `formal_method` / 其他类型的直接角色 | 主任务匹配且证据充分 | 依类型模块进入主方法、候选集、比较或实施部分 |
| `ultra_tip` | How-to、泛主题或 What Is 中，主任务路径完成后的短小、可操作相邻需求 | 主方法/核心答案后；显著标签；相邻场景、最小步骤、支持对象、限制、主任务不适用范围；不计入 Methods |
| `related_supplement` | 相邻需求有独立决策价值，或文章并非 How-to，因而不适合伪装成“Tip” | `Related Supplement` / `Related next step` / 同义本地化模块；位于核心答案或主要比较之后；不是榜单、胜负、主 CTA 或问题答案 |
| `excluded` | 没有真实关系、能力不可核验、与主/相邻对象均不匹配，或即使披露仍有误导/合规风险 | 不进正文；在 Brief/事实表记录范围内排除和证据 |

`related_supplement` 是边界透明的内容角色，不是降低证据门槛的广告位。它可用于所有类型；Type Module 仍决定是否存在读者价值和具体位置。

## 4. 阻断分流，而不是过早停工

| 情况 | 正确状态 | 是否继续主文章 |
| --- | --- | --- |
| 主任务不匹配，但 A–E 可证实 | `adjacent_fit` → Ultra Tip 或 Related Supplement | 是 |
| 主任务不匹配，A–E 尚未完成 | `research_incomplete` | 是；产品不进入正文，回流产品核验 |
| 主任务和相邻需求均不成立 | `scoped_exclusion` | 是；记录排除，不把推荐产品当作文章阻断 |
| 用户明确要求“必须作为主方法/必须出现在正文”，而实时证据否定该要求 | `blocked_waiting_for_user` | 暂停**产品露出决策**，请求用户在排除、改为相邻模块或更换主题之间选择；不要伪造能力 |
| 主题、市场/语言、SERP、关键事实或发布渲染等 P0 不成立 | 对应发布阻断状态 | 否，直到 P0 修复 |

“推荐产品”为建议，不等于“强制主推”。只有任务卡、用户文字或项目配置明确标记 `mandatory_product_inclusion: true` 时，产品冲突才需要用户确认后才可继续该露出决策。即使如此，主文章的研究和非产品内容应尽可能继续完成。

## 5. 必填记录与 QA

在 Brief、事实表及 `release-manifest.json.product.adjacency_assessment` 中记录：

```json
{
  "result": "adjacent_fit",
  "reader_follow_on_need": "主任务后读者需要处理的具体次级对象/决策",
  "relationship_to_primary_task": "同一工作流、资产生命周期或已证实的用户路径",
  "verified_supported_object": "产品当前支持的对象/格式/动作与官方证据摘要",
  "evidence_path": "09_事实与来源核验表.md",
  "primary_task_boundary": "产品明确不能完成的主任务部分",
  "placement": "post_main_methods 或 after_core_answer",
  "module_heading": "正文和 Word 中完全一致的 H2 模块标题",
  "non_substitution_disclosure": "首屏不替代主任务的读者可见说明"
}
```

发布 QA 必须确认：

- 相邻模块不出现在 Quick Answer、Methods Overview、主方法数、榜单/对比结论或主 CTA；其 manifest 模块标题必须真实存在于 Markdown 和 Word H2，且位于 Quick Answer 后（适用时）；
- 相邻模块之前已完成主答案或主方法；
- 文章中有与 manifest 一致的产品官方来源和限制说明；`non_substitution_disclosure` 必须逐字出现在 Markdown 与 Word，而不是只写在 QA 记录中；
- 产品被 `scoped_exclusion` 时，未进入生产正文；
- 任何 `blocked_waiting_for_user` 只针对无法自行决定的强制产品露出，不得冒充整篇文章的完成或失败。
